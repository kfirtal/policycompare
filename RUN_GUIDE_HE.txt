PolicyCompare — מדריך הפעלה וארכיטקטורה
======================================

1. מה הכלי עושה
----------------
הכלי קורא מדיניות מ-CSM ומ-FMC ומפיק שני דוחות נפרדים:

א. דוח חוקים:
   משווה שמות Source Objects, שמות Destination Objects ופרוטוקול/פורטי
   Destination Services. קבוצות שירותים נפתחות לפני ההשוואה.
   ההשוואה נעשית בשני הכיוונים: מה חסר ב-FMC ומה קיים בו מעבר ל-CSM.

ב. דוח אובייקטים:
   מתאים אובייקטים לפי שם וסוג ומשווה את ערכיהם בפועל.
   כולל אובייקטי רשת, שירותים וקבוצות המופנים מהמדיניות, וחברים מקוננים.
   הדוח מציין גם את החוקים המושפעים.

השמות מושווים בדיוק, כולל אותיות גדולות וקטנות. שמות השירותים אינם חלק
מחתימת החוק: הפרוטוקול והפורטים שלהם כן. בדוח האובייקטים נבדקים גם השמות.
סדר החוקים, Action, Enabled, Source Ports, ממשקים ומשתמשים אינם מושווים.
PASS אינו הוכחה לשקילות תעבורה מלאה בין חומות האש.
אין יצירה, שינוי, מחיקה או פריסה של תצורת חומת אש.

יעד התאימות: CSM 4.25 מול FMC 7.6.5 ומעלה.
אימות מול שרתים אמיתיים עדיין נדרש; בדיקות מדומות אינן מוכיחות תאימות לגרסה.

2. מה צריך לפני שמתחילים
------------------------
- Windows עם Python 3.12, כולל pip ו-venv.
- הקבצים צריכים לעבור את תהליך ההלבנה הארגוני.
- גישת HTTPS מהמחשב אל שרתי CSM ו-FMC המורשים לבדיקה.
- חשבונות עם הרשאות לקריאת המדיניות והאובייקטים.
- שם Shared Policy מדויק ב-CSM. מדיניות מקומית למכשיר אינה נתמכת כרגע.
- שם Access Control Policy מדויק ב-FMC והגרסה המותקנת בפועל.
- UUID של domain, אם לחשבון FMC יש גישה לכמה domains.
- חלון איסוף ללא שינויים מקבילים במדיניות, כדי לצמצם אי-עקביות בנתונים.

אין לשלוח סיסמאות בצ'אט או להכניס אותן לקוד, לפקודות או לקובצי הגדרות.
לפני חיבור יש לוודא שאלו השרתים שאושרו לקריאה.

3. פתיחת התיקייה והתקנה חד-פעמית
--------------------------------
חלץ את החבילה לתיקייה חדשה ופתח PowerShell בתיקייה שבה נמצא lab.py.
כל הפקודות במדריך מורצות מתוך אותה תיקייה.
אין צורך להפעיל Activate ואין צורך ב-Git לצורך הרצה.

בדוק Python:

    py -3.12 --version

אם verify_bundle.py קיים בחבילה, בדוק שלמות לפני שינוי או התקנה:

    py -3.12 verify_bundle.py

צפוי PASS. בתיקיית קוד נקייה ללא כלי האריזה ייתכן שקובץ זה אינו קיים.
אם נמסר קובץ ZIP.sha256, יש להשוות גם את חתימת ה-ZIP לפי תהליך ההעברה.
חתימות בודקות שלמות; הן אינן אישור הלבנה ארגוני.

צור סביבת Python נפרדת לפרויקט:

    py -3.12 -m venv .venv

בחר את קובץ התלויות הקיים. בחבילה המלאה יש requirements-offline.txt;
בתיקיית העבודה הנקייה התלויות הנעולות נמצאות ב-requirements.txt:

    $requirementsFile = '.\requirements.txt'
    if (Test-Path '.\requirements-offline.txt') {
        $requirementsFile = '.\requirements-offline.txt'
    }

אפשרות א — התקנה ללא גישה לרשת, אם תיקיית wheelhouse נכללה בחבילה:

    .\.venv\Scripts\python.exe -m pip --isolated install --disable-pip-version-check --no-cache-dir --no-index --find-links .\wheelhouse --only-binary=:all: --require-hashes -r $requirementsFile

אפשרות ב — התקנה דרך Artifactory, אם pip כבר מוגדר למאגר הפנימי המאושר:

    .\.venv\Scripts\python.exe -m pip install --disable-pip-version-check --no-cache-dir --only-binary=:all: --require-hashes -r $requirementsFile

יש לוודא שגם index וגם extra-index, אם הוגדר, פונים רק למאגרים המאושרים.
אין צורך להריץ את שתי אפשרויות ההתקנה. בחר אחת ובדוק את תקינות התלויות:

    .\.venv\Scripts\python.exe -m pip --isolated check

אין לעקוף שגיאת hash: אם Artifactory מספק קובץ שונה, צריך לאשר ולבדוק נעילה
מעודכנת, או להשתמש בקובצי ה-wheel המצורפים לאחר אישורם הארגוני.

4. בדיקות מקומיות ללא שרתים
---------------------------
אם תיקיית tests קיימת בחבילה, הרץ:

    .\.venv\Scripts\python.exe -m unittest discover -s tests -q

בחבילה המעודכנת הכוללת את בדיקות TLS צפויות 121 בדיקות שעוברות.
הבדיקות משתמשות בתשובות מדומות ואינן מתחברות לשרתי Cisco.
בתיקיית העבודה הנקייה הבדיקות הועברו לגיבוי, ולכן שלב זה חל על החבילה המלאה.

5. הגדרת פרטי ההרצה
-------------------
העתק ל-PowerShell והחלף את הכתובות והשמות הסינתטיים בערכים המורשים שלך:

    $labArgs = @(
        '--csm-url', 'https://csm.example.invalid/nbi'
        '--fmc-url', 'https://fmc.example.invalid'
        '--csm-policy', 'CSM-POLICY-NAME'
        '--fmc-policy', 'FMC-POLICY-NAME'
        '--fmc-version', '7.6.5'
        '--output-dir', 'reports/work-001'
        '--timeout', '30'
        '--insecure'
    )

הסבר הפרמטרים:
--csm-url      כתובת CSM עם /nbi בסוף. אפשר לציין פורט בכתובת לפי הצורך.
--fmc-url      כתובת FMC בלבד, ללא /api.
--csm-policy   השם המדויק של ה-Shared Policy.
--fmc-policy   השם המדויק של ה-Access Control Policy.
--fmc-version  הגרסה המותקנת בפועל; זהו תיעוד מוצהר, לא זיהוי אוטומטי.
--output-dir   תיקיית הרצה חדשה בתוך reports של הפרויקט.
--timeout      זמן המתנה לכל בקשת HTTP, בשניות; לא משך ההרצה הכולל.
--insecure     דילוג על אימות תעודות TLS בשני שרתי Cisco להרצה הנוכחית.

הדגל --insecure מתאים לשרתי הפיתוח עם תעודה עצמית או לא מהימנה.
HTTPS עדיין נדרש. הדגל אינו פותר העדר שרת HTTPS, בעיית רשת או שגיאת הזדהות.
השימוש מתועד ב-run.json. בלי הדגל אימות התעודות פעיל.
הדגל אינו משנה את אימות התעודות של pip או של Artifactory.

אם רוצים אימות עם CA ארגוני, הסר את השורה '--insecure' מהמערך והוסף,
לפי הצורך, נתיבים לקובצי PEM תקינים שסופקו בארגון:

    $labArgs += @('--csm-ca', 'C:\WorkCA\csm-ca.pem')
    $labArgs += @('--fmc-ca', 'C:\WorkCA\fmc-ca.pem')

אין לשלב --insecure עם --csm-ca או --fmc-ca.

אם לחשבון FMC יש כמה domains, הוסף את ה-UUID המתאים:

    $labArgs += @('--fmc-domain', 'DOMAIN-UUID')

הנתיבים וה-UUID כאן הם דוגמאות שיש להחליף, ולא קבצים או מזהים שנכללו בחבילה.

6. בדיקת הגדרות והרצה מול השרתים
--------------------------------
תחילה בדוק הגדרות בלבד:

    .\.venv\Scripts\python.exe lab.py @labArgs

ללא --connect אין בקשות לשרתים ואין בקשת סיסמה.
הבדיקה אינה מוכיחה זמינות שרת, תקינות ההרשאות או התאמה לגרסת API.

לאחר האישור לחיבור לשרתים המסוימים, הפעל איסוף והשוואה:

    .\.venv\Scripts\python.exe lab.py @labArgs --connect
    $LASTEXITCODE

התוכנית תשאל שם משתמש וסיסמה ל-CSM, ובהמשך ל-FMC.
הסיסמה אינה מוצגת בזמן ההקלדה. אם לא ניתן להסתיר אותה, ההזדהות נעצרת.
אין צורך להריץ את csm.py או fmc.py בנפרד; lab.py מפעיל אותם.

בהרצה חוזרת בחר שם תיקייה חדש. למשל, בנה שוב את מערך $labArgs עם
'reports/work-002' במקום 'reports/work-001'. אין דריסת תיקיית הרצה קיימת.
אין להוסיף --allow-empty כדי לעקוף כשל; הוא מיועד רק למדיניות ריקה במכוון.

7. לאן מגיעות התוצאות
---------------------
לפי הדוגמה, התוצאות נמצאות בתת-התיקייה reports\work-001 בתיקיית הפרויקט:

    PolicyCompare\
        lab.py
        compare.py
        ...
        reports\
            work-001\
                rules_report.txt
                rules_report.json
                objects_report.txt
                objects_report.json
                csm.snapshot.json
                fmc.snapshot.json
                run.json

rules_report.txt / rules_report.json
    חוקים שקיימים ב-CSM וחסרים ב-FMC, וחוקים שקיימים ב-FMC וחסרים ב-CSM.
    ההתאמה היא לפי שלושת השדות בלבד, ללא תלות בסדר ובמספר החוק.

objects_report.txt / objects_report.json
    אובייקטים חסרים או עודפים, ערכים שונים והחוקים המושפעים בכל צד.
    נבדקים האובייקטים המופנים מהמדיניות, ולא כל ספריית האובייקטים בשרת.

csm.snapshot.json / fmc.snapshot.json
    הנתונים המנורמלים שנאספו מכל מערכת, לשחזור ההשוואה ללא חיבור נוסף.
    הם אינם תגובות API גולמיות ואינם מכילים סיסמאות או טוקנים.

run.json
    מצב ההרצה, זמני UTC, גרסאות מוצהרות, snapshots שהושלמו, שלבי כשל,
    כשלי ניקוי ומצב אימות התעודות תחת tls_verification.

בכשל ייתכן שחלק מהקבצים לא נוצרו, או שנשמר רק snapshot של צד אחד.
כשל כתיבה עשוי למנוע גם שמירת run.json. תיקייה חלקית אינה הוכחת הצלחה.
דוחות ו-snapshots מכילים שמות וערכי תשתית; הם נשארים ברשת העבודה.

8. איך מפרשים את התוצאה
-----------------------
PASS           התאמה בתחום שנבדק והנתונים הנדרשים זמינים.
FAIL           נמצאו פערים.
INDETERMINATE  המידע אינו שלם, אינו נתמך או שהתרחש כשל.

קודי יציאה: 0 = PASS, 1 = FAIL, 2 = INDETERMINATE.
התוצאה הכוללת היא INDETERMINATE אם אחת הבדיקות אינה שלמה; אחרת FAIL
אם יש פער, ואחרת PASS. כשל ניקוי חיבורים מסומן גם הוא ברמת ההרצה.

אותו שם אובייקט רשת עם כתובת אחרת יכול לתת PASS בחוקים ו-FAIL באובייקטים.
כשל איסוף אינו מדיניות ריקה ואינו PASS. במקרה של כשל בדוק תחילה את run.json.

9. השוואה חוזרת ללא חיבור לשרתים
--------------------------------
אם שני snapshots נשמרו, אפשר להריץ:

    .\.venv\Scripts\python.exe compare.py reports/work-001/csm.snapshot.json reports/work-001/fmc.snapshot.json --output-dir reports/replay-001

הפקודה מפיקה שוב את שני הדוחות מהנתונים המקומיים, בלי להזדהות או לפנות לשרת.
גם כאן תיקיית הפלט חייבת להיות חדשה כדי לא לדרוס דוחות קיימים.

10. ארכיטקטורת הקבצים
---------------------
lab.py
    נקודת הכניסה לאיסוף חי. קורא ארגומנטים, בודק הגדרות, מבקש הזדהות,
    מפעיל את שני הלקוחות, שומר snapshots, מפעיל השוואה וסוגר חיבורים.

csm.py
    לקוח CSM. בונה בקשות XML, קורא את כל דפי המדיניות ומפענח אובייקטים
    וקבוצות מקוננות. מחזיר רשימת Rule. אובייקטים נשמרים במטמון למשך האיסוף.

fmc.py
    לקוח FMC REST. מקבל טוקן, מאתר מדיניות לפי שם, אוסף דפים ומפענח JSON
    של חוקים ואובייקטים. מחזיר רשימת Rule באותו מבנה משותף.

rule.py
    מחלקת Rule: מזהה חוק, שלושת שדות ההשוואה, מלאי אובייקטים ובעיות איסוף.
    record_object רושמת אובייקטים בעלי שם וערכיהם לצורך הדוח השני.

compare.py
    יוצר חתימות משלושת שדות החוק ומשווה בשני הכיוונים. משווה בנפרד את ערכי
    האובייקטים לפי שם וסוג. מפיק את שני הדוחות. יכול לפעול גם על snapshots בלבד.

normalization.py
    מנרמל כתובות, פרוטוקולים ופורטים כדי לזהות ייצוגים שקולים ולא הבדלי כתיב.
    לדוגמה: TCP ו-6; כתובת מארח וכתובת /32; טווחי פורטים חופפים או רצופים.

transport.py
    שכבת HTTP משותפת: HTTPS, אימות תעודות, timeout, טיפול מוגבל ב-429,
    חסימת redirects וסגירת session. יצירת לקוח אינה שולחת בקשת HTTP.

response_validation.py
    בדיקות מבנה לרשימות אובייקטים ולמזהים בתשובות JSON.

snapshots.py
    שמירה וטעינה של נתונים מנורמלים. דוחה מבנים לא תקינים, שדות JSON
    כפולים ומזהי חוקים חוזרים. משמש לשחזור השוואה ללא שרתים.

errors.py
    סוגי השגיאות APIError ו-ValidationError, כדי לטפל בכשלים באופן עקבי.

requirements.txt
    גרסאות תלויות Python וחתימותיהן בתיקיית העבודה הנקייה.

README.md / RUN_GUIDE_HE.txt
    הסבר מקוצר והוראות הפעלה מלאות. אינם מבצעים פעולות.

קבצים נוספים בחבילת ההעברה המלאה:
    tests/                    בדיקות לא-מקוונות עם תשובות מדומות.
    examples/                 נתוני דוגמה סינתטיים.
    wheelhouse/               תלויות להתקנה ללא אינטרנט.
    requirements-offline.txt  נעילת תלויות להעברה.
    verify_bundle.py          אימות קובצי החבילה מול MANIFEST.json.
    package_transfer.py       כלי בניית חבילה בסביבת הפיתוח; אינו נדרש להרצה.
    MANIFEST.json             שמות קבצים, גדלים, SHA-256 ומזהה גרסת מקור.
    מסמכי העברה ותלויות       הוראות נוספות ופירוט גרסאות ורישיונות.

תיקיות שנוצרות בזמן שימוש:
    .venv/        סביבת Python מקומית; אינה קוד הפרויקט ואין להעבירה בין מחשבים.
    reports/      תוצאות הרצות ונתונים שנאספו.
    __pycache__/  מטמון אוטומטי של Python, אם נוצר.

זרימת הנתונים:
    lab.py -> csm.py / fmc.py -> רשימות Rule -> compare.py -> שני דוחות
    csm.py / fmc.py -> transport.py -> בקשות HTTPS
    normalization.py מנרמל את הערכים בזמן הפענוח וההשוואה.
    snapshots.py שומר את נתוני ההשוואה ומאפשר compare.py ללא חיבור.

11. מגבלות וטיפול ראשוני בתקלות
--------------------------------
- שגיאת Python או pip: ודא Python 3.12 והשתמש ב-python.exe של .venv.
- אי-התאמה ב-hash: אל תבטל את האימות; בדוק את הקבצים והגרסאות המאושרים.
- תיקיית פלט קיימת: בחר תיקייה חדשה, ולא אותה תיקייה מהרצה קודמת.
- כשל ברשת או בהזדהות: בדוק גישה, כתובות, פורטים והרשאות במערכת המתאימה.
- כמה domains ב-FMC: ספק --fmc-domain עם UUID מורשה.
- שגיאת תעודה: השתמש ב-CA המתאים, או בדגל --insecure לשרתי הפיתוח המורשים.
- שגיאת איסוף: בדוק error_details ב-run.json, ובעיקר stage ו-category.
- בשיתוף תקלה מחוץ לרשת, אין להעביר דוחות או snapshots אמיתיים ללא צנזור ואישור.

FQDN, ICMP, פרוטוקולים שאינם IP-any/TCP/UDP, מדיניות CSM מקומית ו-overrides
לפי מכשיר אינם נתמכים במסלול הנוכחי. אין חידוש טוקן FMC אוטומטי.
NAT, ניתוב, מצב פריסה וברירת המחדל אינם בתחום ההשוואה.
